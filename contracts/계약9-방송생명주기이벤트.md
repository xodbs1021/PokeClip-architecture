# 계약9 — Broadcast Lifecycle Event (Media → Chat · Clip)

> For future Claude: PokeClip **인터페이스 계약9**(11-역할분담 계약 9종 중 하나). 방송 시작/종료 사실을 Media가 발행하고 Chat Collector·Clip Service가 각자 독립 소비한다. 이 문서는 2026-08-16 **초안 발행** — 근거 정본: [11_역할분담](../11_Pokeclip_역할분담.md) 계약 표 9행 · [ADR-016](../adr/ADR-016_방송이벤트_SNS_SQS팬아웃.md)(envelope·전이·역순 방어 확정) · [10_데이터플로우](../10_Pokeclip_데이터플로우.md)(payload 예시). 이 문서가 정본을 앞서 확정하지 않는다 — 정본과 다르게 읽히면 정본이 이긴다.

## 1. 토폴로지 (ADR-016)

```
Media Origin ──publish──▶ SNS FIFO broadcast-lifecycle.fifo
                             ├─(Raw Message Delivery)─▶ SQS FIFO broadcast-lifecycle-chat.fifo (+전용 DLQ) ─▶ Chat Collector
                             └─(Raw Message Delivery)─▶ SQS FIFO broadcast-lifecycle-clip.fifo (+전용 DLQ) ─▶ Clip Service
```

- 단일 큐 공유 금지(경쟁 소비), Media의 이중 직접 발행 금지(부분 실패 복구가 인제스트에 결합) — 기각 근거는 ADR-016.

## 2. 발행 규칙 (Media = 생산자, 1번)

- 방송 사실마다 **논리 이벤트 하나**를 만든다.
- `MessageGroupId = streamId` — 같은 방송의 시작→종료 순서 보존.
- `MessageDeduplicationId = eventId` — at-least-once 전달에서의 멱등 좌표.
- 발행 실패·결과 불명확 시 **새 이벤트를 만들지 않고 동일한 `eventId`로 재시도**한다.
- Media는 렌더·AI·업로드 **잡을 만들지 않는다** — 그것은 Clip Service의 역할이다(10번: 인제스트 노드를 비즈니스 로직에 결합시키지 않기 위함).

## 3. Envelope (ADR-016 확정) · 이벤트 2종

- **envelope 필드(확정):** `schemaVersion` · `eventId` · `eventType` · `occurredAt` · `streamId` · `streamerId` · `sequence` · `traceId` · `payload`.
- `broadcast.started`의 `payload.trackManifest`는 Media Origin이 보유한 A3 등록본의 **`manifestVersion` 스냅샷**이다(ADR-016 — A3는 기능명세서의 기능 ID, 등록 경로는 계약4A `track-manifest`).

| 이벤트 | payload 요지 (10번 초안 기준 — 세부 필드 확정은 10번이 갱신 정본) | 소비자가 하는 일 |
|---|---|---|
| `broadcast.started` | 트랙 매니페스트(오디오 트랙 수·라벨 — `manifestVersion` 스냅샷 포함), 시작 시각 | Chat: 채팅 수집 시작 · Clip: broadcasts 레코드 생성, 라이브 상태 등록 |
| `broadcast.ended` | 종료 시각, 최종 세그먼트 범위 | Chat: 수집 종료 · Clip: 종료 처리, VOD 레코드 확정 |

## 4. 소비 규칙 (Chat=2번 · Clip=3번, ADR-016 확정)

- 전달은 **at-least-once** — 소비자는 `eventId`를 멱등 키로 처리한다.
- 상태 전이는 **`INITIAL → LIVE → ENDED` 한 방향**으로만.
- **역순 방어:** `INITIAL` 상태에서 `broadcast.ended`를 받으면 — Clip Service는 ended placeholder를 PostgreSQL에 upsert, Chat Collector는 Redis에 `ENDED` tombstone(TTL 24h)을 남긴 뒤 ack와 알람. 이후 **더 낮은 `sequence`의 started는 무시**한다. 처리 예외만 DLQ로 이동한다.
- 순서는 `MessageGroupId=streamId` 단위로만 보장된다.
- 실패 메시지는 각자 전용 DLQ로 — 서로의 소비 실패에 영향받지 않는다.

## 5. 당사자·승인권 (11_역할분담 표 9행)

- **설계·승인·생산 = 1번(Media)** · Chat 소비 = 2번 · Clip 소비 = 3번.
