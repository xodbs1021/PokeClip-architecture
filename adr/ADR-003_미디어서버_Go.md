# ADR-003: 미디어 서버 — Go 직접 구현 (Media Origin)

- **상태**: 채택
- **결정일**: 2026-07-20
- **관련**: [ADR-001](ADR-001_송출프로토콜.md) · [ADR-005](ADR-005_저장일원화.md) · [ADR-007](ADR-007_스택배치.md) · [ADR-013](ADR-013_인프라.md)
- **반영 산출물**: 3_SA · 4_SysA · 5_CA

## 컨텍스트

SRT 수신부터 LL-HLS 서빙까지의 미디어 계층을 직접 만들 것인가, 관리형 서비스나 오픈소스로 대체할 것인가. 취업 포트폴리오로서의 어필과 3인 팀의 구현 리스크 사이의 균형이 쟁점.

## 결정

SRT 수신·TS 디먹스·CMAF 세그먼트화·LL-HLS 서빙(DVR)·S3 적재·VOD 확정·방송 이벤트 발행을 Go로 직접 구현한다. MediaMTX(Go로 SRT+LL-HLS를 구현한 오픈소스)를 참조 레퍼런스로 삼는다.

## 근거

- 이 계층이 프로젝트의 핵심 어필 — 관리형(MediaLive류)이나 오픈소스 포크로 대체하면 "만든 사람"이 아니라 "설정한 사람"이 된다.
- 고루틴 동시성 모델이 "스트리머 N × (수신→디먹스→세그먼트화→적재)" 파이프라인에 정확히 부합.
- 팀 개발 방식("Claude가 짜고 사람이 리뷰")에 최적: Go는 AI 생성 코드 품질과 Java 개발자의 리뷰 가능성이 동시에 높은 언어.

## 검토한 대안

- **(a) C/C++ 바닥부터**: 어필 최상이나 메모리·스레딩 디버깅 난도 최악, Java 팀 리뷰 불가 → 품질 게이트 상실. 탈락.
- **(c) FFmpeg/GStreamer 프로세스 오케스트레이션**: 구현 최속이나 Apple LL-HLS 파트·DVR 매니페스트 제어 한계, 6트랙 alternate rendition 명령 복잡, 어필 격하 → **백업 플랜으로 보존**. 미디어 계층 출력을 '세그먼트 계약'(디렉토리·매니페스트 규격) 인터페이스로 정의해 최악 시 (b)→(c) 교체 가능하게 설계(일정 리스크 헤지).
- **(d) OvenMediaEngine 포크**: 기능 즉시 확보하나 대형 C++ 코드베이스 이해 선행, 멀티오디오 rendition 지원 불확실, "갖다 썼네" 리스크. 탈락.
